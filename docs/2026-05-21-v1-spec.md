# Low-Cost Cloud-Native Plot Portal Spec

## Summary

Build a small web portal for submitting natural-language plotting requests and viewing generated results. The system is designed for extremely low traffic, but must remain responsive when idle and must run expensive analysis work in separate custom containers only when needed.

The architecture separates the always-on web experience from scale-to-zero plot execution:

- A tiny always-on web app handles login, job submission, status pages, and result display.
- Persistent metadata is stored in a relational database.
- Job requests are sent through a queue.
- Generated artifacts are stored in object/blob storage.
- Plot execution runs in isolated job containers that start only when work exists, then exit.
- Secrets are provided through environment/local secret files in development and through managed cloud secret storage in production.

This design should support both local Docker Compose development and cheap Azure deployment.

## Goals

- Keep the homepage and job pages responsive even when no jobs are running.
- Keep idle cloud cost low.
- Run at most one plot job at a time by default.
- Run plot code in a separate custom container image with ROOT, Python, ServiceX dependencies, and other analysis packages installed.
- Preserve user accounts, approvals, job history, prompts, generated scripts, logs, and artifact metadata.
- Store generated files outside the database.
- Keep secrets out of git, images, queue messages, and logs.
- Make local development close enough to production that most behavior can be tested without Azure.

## Non-Goals

- Multi-user high-concurrency operation.
- Kubernetes.
- Distributed worker pools.
- Real-time collaboration.
- Zero-downtime deploys.
- Complex autoscaling.
- Running analysis work inside HTTP request handlers.
- Having the web app directly start Docker containers in production.

## Target Production Architecture

### Services

1. **Web App**
   - Runs as a small always-on container.
   - Handles HTTP requests, auth, job submission, status pages, result pages, admin pages.
   - Reads/writes relational metadata.
   - Writes queue messages.
   - Reads artifact metadata and generates artifact links.
   - Calls OpenAI where needed for web-side behavior.
   - Does not run plot jobs.
   - Does not require Docker access.

2. **Relational Database**
   - Stores durable app metadata:
     - users
     - approval state
     - jobs
     - job status
     - prompt text
     - selected backend profile
     - timestamps
     - generated code text if small enough
     - artifact metadata
     - failure messages
   - Preferred initial options:
     - Azure SQL Basic/low tier, if Django ORM compatibility is acceptable.
     - Azure Database for PostgreSQL low tier, if PostgreSQL compatibility is preferred.
   - The app should keep DB usage tiny and connection counts low.

3. **Queue**
   - Stores job start requests.
   - Production target: Azure Storage Queue.
   - Queue message should contain only minimal routing data:

     ```json
     {
       "job_id": "uuid",
       "backend_profile": "servicex_awkward"
     }
     ```

   - Do not put prompts, secrets, generated code, or large payloads in the queue.

4. **Artifact Storage**
   - Production target: Azure Blob Storage.
   - Stores:
     - plot images
     - markdown reports
     - generated scripts
     - stdout/stderr logs if retained
     - downloadable result bundles
   - Database stores blob keys and metadata, not large binary content.

5. **Plot Job Container**
   - Runs as an Azure Container Apps Job or equivalent cloud job primitive.
   - Uses a custom image with ROOT, Python, analysis packages, and backend tooling installed.
     - Possible dockerfile that exists for similar running (awkward version): <https://github.com/gordonwatts/hep-data-llm/blob/main/Docker/Dockerfile>
     - Possible dockerfile for the root workflow: <https://github.com/gordonwatts/hep-data-llm/blob/main/Docker/Dockerfile.RDF>
   - Starts when a queue message exists or when explicitly invoked for a job.
   - Reads job metadata from the database.
   - Reads/writes artifacts from/to Blob Storage.
   - Updates job status in the database.
   - Exits after one job.
   - Default max concurrency: 1.

6. **Secret Store**
   - Production target: Azure Key Vault.
   - Secrets:
     - web OpenAI API key
     - Django/app secret key
     - database credentials if not using managed identity
     - GitHub/OAuth credentials if used
     - ServiceX config
     - plot-runner OpenAI key if needed
   - Use managed identities to grant separate access:
     - web identity can read web secrets
     - plot-job identity can read plot execution secrets
   - Avoid sharing all secrets with all services.

## Target Local Architecture

Local development should use Docker Compose and local emulators.

### Local Services

1. `web`
   - Same web app code as production.
   - Talks to local Postgres.
   - Talks to Azurite queue/blob endpoints.
   - Reads local secrets from `.env` or mounted files.

2. `postgres`
   - Local durable database.
   - Stores the same metadata schema as production.

3. `azurite`
   - Azure Storage emulator.
   - Provides local Queue and Blob behavior.
   - Used to test queue and artifact flows without Azure.

4. `local-job-runner`
   - Small local process that polls the local queue.
   - Claims one message.
   - Starts or invokes the plot-runner container locally.
   - Updates job status.
   - Deletes queue messages only after the job reaches a terminal state.

5. `plot-runner`
   - Same image concept as production plot job.
   - Has ROOT/Python/custom analysis tools installed.
   - Receives job id and config.
   - Reads/writes local Azurite blobs or mounted artifact paths.
   - Reads local `servicex.yaml` from a mounted secret path.

### Local Flow

1. User submits a plot request in the web UI.
2. Web creates a `Job` row in Postgres with status `queued`.
3. Web writes a queue message to Azurite:

   ```json
   {
     "job_id": "uuid",
     "backend_profile": "servicex_awkward"
   }
   ```

4. `local-job-runner` receives the message.
5. Runner marks job `running`.
6. Runner invokes the plot-runner container or plot-runner command.
7. Plot runner reads job details from DB.
8. Plot runner runs analysis.
9. Plot runner writes outputs to Azurite Blob Storage.
10. Plot runner updates DB with status, artifact records, generated code, failure text, and timing.
11. Runner deletes the queue message after successful terminal update.
12. Web shows updated status and results.

## Status Semantics

- `queued`: job row exists and queue message has been written.
- `running`: plot job has claimed work and started execution.
- `completed`: plot job finished successfully and artifacts are recorded.
- `failed`: plot job reached terminal failure.
- `cancelled`: user/admin cancelled before execution or at a safe checkpoint.

Queue messages must not be considered the source of truth. The database job row is the durable source of truth.

## Plot Runner Contract

The plot runner should support a command like:

```bash
plot-runner run --job-id <uuid>
```

The runner obtains all required context through configured services:

- database connection
- blob storage connection
- secret provider
- backend profile
- job row

The plot runner must:

1. Load job by id.
2. Refuse to process if job is not `queued` or explicitly claimed.
3. Mark job `running`.
4. Create an isolated working directory.
5. Run analysis.
6. Upload artifacts.
7. Write artifact metadata.
8. Mark job `completed` or `failed`.
9. Avoid logging secrets.
10. Exit.

## Interfaces / Adapters

Use small adapter interfaces so local and Azure implementations can differ without changing app logic.

### QueueClient

Methods:

- `enqueue_job(job_id, backend_profile) -> message_id`
- `receive_messages(max_messages=1)`
- `delete_message(message)`
- `abandon_message(message)`

Local implementation:

- Azurite Storage Queue.

Production implementation:

- Azure Storage Queue.

### ArtifactStore

Methods:

- `put_artifact(job_id, local_path, artifact_kind, content_type) -> ArtifactRef`
- `get_read_url(artifact_ref) -> url`
- `delete_artifacts_for_job(job_id)`

Local implementation:

- Azurite Blob Storage, or filesystem for very early development.

Production implementation:

- Azure Blob Storage.

### SecretProvider

Methods:

- `get_secret(name) -> str`
- `get_file_secret(name) -> path or text`

Local implementation:

- `.env`
- mounted files such as `./secrets/servicex.yaml`

Production implementation:

- Azure Key Vault through managed identity.

### JobStore

Usually the ORM/database layer. It must expose safe operations for:

- create queued job
- claim job
- mark running
- mark completed
- mark failed
- mark cancelled
- list current user jobs
- enforce user ownership

### PlotExecutor

Local implementation:

- run plot-runner container through Docker Compose or Docker CLI.

Production implementation:

- Azure Container Apps Job execution, or an event-triggered Container Apps Job reading from queue.

## Concurrency Rules

Default production behavior:

- web app: `minReplicas=1`, `maxReplicas=1` or `2`
- plot jobs: max concurrent executions `1`
- queue message visibility timeout must exceed expected job startup/claim window
- job hard timeout should be explicit
- no more than one `running` job at a time unless intentionally changed later

The database should enforce or help enforce single-active-job semantics. Do not rely only on queue behavior.

## Secrets

### Web Secrets

- app secret key
- OpenAI API key for web-side model calls
- auth/OAuth client secret
- database connection credentials if needed

### Plot Job Secrets

- ServiceX config
- OpenAI API key if plot execution calls OpenAI
- any backend-specific tokens
- storage/database credentials if not using managed identity

### Rules

- Never write secrets into queue messages.
- Never write secrets into job metadata.
- Never bake secrets into container images.
- Never print secrets in logs.
- Prefer managed identity in Azure.
- Prefer local mounted files in development.

## Deployment Strategy

### Local

Use:

```bash
docker compose up
```

Local Compose should start:

- web
- postgres
- azurite
- local-job-runner
- optional plot-runner image build

### Azure

Recommended Azure resources:

- Azure Container Apps for web
- Azure Container Apps Job for plot execution
- Azure Storage Account for Queue and Blob
- Azure Key Vault
- Small relational database
- Managed identities for web and plot job
- Optional Application Insights/logging, kept minimal to control cost

## Cost Strategy

Keep always-on compute minimal:

- one tiny web replica
- no always-on worker
- no VM
- no Kubernetes
- no always-on analysis container

Pay per use for:

- plot job execution
- storage transactions
- queue operations
- blob storage
- database usage/storage

Database is the main persistent cost decision. Keep the schema small, avoid chatty polling, and avoid unnecessary always-open DB connections.

## Web UI Requirements

Required pages:

- home / submit plot
- job detail
- job history
- clone/edit/resubmit
- login/logout
- approval status
- admin approvals
- admin job list

Job detail page should poll lightly while status is `queued` or `running`.

Polling interval:

- default 1-2 seconds locally
- consider 3-5 seconds in production if costs or DB load matter

## Admin Requirements

Admins can:

- approve/reject users
- view all jobs
- inspect job status and failure messages
- cancel queued jobs
- optionally delete jobs/artifacts

Regular users can only see their own jobs and artifacts.

## Failure Handling

- If queue message exists but job row is missing: log and discard message.
- If job is already terminal: discard message.
- If plot runner crashes before marking terminal:
  - message should eventually become visible again or job should be recovered by a watchdog.
- If job exceeds hard timeout:
  - mark failed
  - record timeout message
- If artifact upload fails after analysis succeeds:
  - mark failed or partially failed with explicit message
- If status update fails:
  - do not delete queue message until durable state is known.

## Cancellation

Minimum behavior:

- users/admins may cancel `queued` jobs.
- running cancellation can be deferred unless easy to implement safely.

Future behavior:

- plot runner checks cancellation state at safe checkpoints.
- running job exits early and marks `cancelled`.

## Observability

Keep lightweight logs:

- job id
- status transitions
- runner start/end
- artifact upload success/failure
- exception summaries

Avoid logging:

- full secrets
- tokens
- ServiceX config content
- private user data beyond what is necessary for debugging

## Open Design Decisions

- Which relational database is preferred for the new repo:
  - PostgreSQL for compatibility with current Django expectations.
  - Azure SQL Basic/serverless for potential low-cost managed persistence.
- Whether production job triggering should be:
  - queue-triggered Container Apps Job, or
  - web explicitly starts a Container Apps Job after writing the queue message.
- Whether local artifact storage should begin with:
  - Azurite Blob Storage from day one, or
  - filesystem first, then Azurite.
- Whether generated code should be stored directly in DB or as a blob artifact with preview text in DB.
- Whether ServiceX config should be mounted as a file secret or provided as secret text written to a temp file at runtime.

## Acceptance Criteria

The design is acceptable when:

- The homepage stays available with only the tiny web app running.
- No analysis container is running while idle.
- A submitted job persists to DB and queue.
- A plot job container starts only when work exists.
- Plot job outputs are saved to blob/object storage.
- Job history survives web app restart.
- Artifacts survive app restart.
- Secrets are not committed, baked into images, or placed in queue messages.
- Local development can exercise the full queue/job/artifact flow without Azure.
- Azure deployment can run one real plot job end to end.
